## FunctionDef _make_rich_handler
**_make_rich_handler**: The function of _make_rich_handler is to instantiate and return a pre-configured RichHandler logging handler optimized for console output with enhanced formatting capabilities.
**parameters**: This function does not accept any parameters.
**Code Description**: The function creates an instance of RichHandler from the rich.logging module and configures it with specific display options. It binds the handler to a shared console object, enables rich-formatted tracebacks while disabling local variable inspection for cleaner output, and activates timestamp and file path display in log records. Markup support is also enabled to allow formatted text within log messages. Within the project architecture, this function serves as a factory method exclusively called by configure_logging. The returned handler replaces default logging handlers on the root logger and specific Discord-related loggers, ensuring that all application logs are consistently rendered with colorized output, readable tracebacks, and contextual metadata directly to the console.
**Note**: The function relies on an external console variable being defined in the same module or imported beforehand. It does not handle logger configuration levels or handler attachment; those responsibilities belong to the caller. Ensure that the rich library is installed and properly initialized before invoking this function.
**Output Example**: <rich.logging.RichHandler object at 0x7f8a1b2c3d40>
## FunctionDef configure_logging(level)
**configure_logging**: The function of configure_logging is to initialize and apply a custom RichHandler-based logging configuration to the root logger and specific Discord-related loggers, enabling colorized console output and readable tracebacks.
**parameters**: The parameters of this Function.
· level: int = logging.INFO - Specifies the minimum severity level for capturing log messages. Defaults to INFO.
**Code Description**: This function orchestrates the application's logging setup by first invoking _make_rich_handler to obtain a pre-configured RichHandler instance optimized for console rendering. It then retrieves the root logger via logging.getLogger(), removes any existing handlers, sets its effective level to the provided level parameter, and attaches the new handler. Subsequently, it iterates through a predefined collection of Discord-related logger names (_DISCORD_LOGGERS), clears their existing handlers, enables log propagation to the parent logger, and synchronizes their logging level with the root logger. This ensures consistent formatting and output routing across the application. The function is invoked exactly once during application initialization in app.py/main, preceding the instantiation of core components like TrackerScraper, RegistrationStore, FeelsStore, and the MarvelLoggerBot. By centralizing logging configuration here, it guarantees that all subsequent log records from the bot and its dependencies are uniformly processed through the RichHandler before any Discord API interactions occur.
**Note**: The function assumes _DISCORD_LOGGERS is defined elsewhere in the module as an iterable of logger names. It does not validate or create this collection. The RichHandler requires the rich library to be installed and properly initialized. Since it explicitly clears existing handlers on both the root and Discord loggers, calling this function multiple times will reset the logging configuration each time. Ensure this function is called early in the application lifecycle before any logging occurs to prevent default handler interference or duplicate output.
## FunctionDef scrape_progress
**scrape_progress**: The function of scrape_progress is to create and return a configured progress instance designed for displaying an indeterminate spinner during asynchronous web scraping operations.
**parameters**: This function does not accept any parameters.
**Code Description**: The scrape_progress function initializes and returns a rich.progress.Progress object specifically configured for monitoring ongoing network requests where the total duration or completion percentage is unknown. It configures three distinct columns: a cyan-colored SpinnerColumn to indicate active processing, a TextColumn to render dynamic task descriptions, and a TimeElapsedColumn to track operation duration. The instance is bound to an external console object for consistent terminal output formatting across the application. By setting transient=True, the progress bar is automatically cleared from the terminal upon exiting its context manager block, preventing visual clutter after the scraping task completes or terminates. In the project architecture, this function is utilized within the TrackerScraper._scrape_json method to wrap asynchronous HTTP fetch operations. The caller instantiates the progress bar via a context manager, adds an indeterminate task with a descriptive label using total=None, and executes the network request inside the block. This design ensures users receive real-time feedback on the scraping status without blocking the main event loop, while the transient cleanup behavior guarantees a clean terminal state once the data retrieval finishes or an exception occurs.
**Note**: The function relies on an external console object that must be defined in the same module or imported prior to calling this function. It is strictly intended for use as a context manager and should not be instantiated directly without the with statement, as the transient cleanup behavior depends on proper context exit. The underlying rich.progress library must be available in the environment.
**Output Example**: [cyan]⠋[/] Scraping user123 on Tracker.gg… 0:00:04
