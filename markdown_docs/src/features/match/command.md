## FunctionDef _resolve_username(interaction, username, store)
**_resolve_username**: The function of _resolve_username is to determine the appropriate Tracker.gg username for a Discord interaction by validating explicit input or falling back to a user's registered profile, returning None if resolution fails.
**parameters**: The parameters of this Function.
· interaction: A discord.Interaction object representing the incoming slash command execution context.
· username: An optional string containing the tracker username explicitly provided by the user in the command arguments.
· store: A RegistrationStore instance providing asynchronous access to the SQLite database for retrieving user registration records.
**Code Description**: This async utility function implements a two-tier resolution strategy for tracker usernames within Discord slash commands. When an explicit username is supplied, it trims leading and trailing whitespace, then delegates validation to validate_tracker_username. If the validation returns an error string, the function immediately sends an ephemeral error embed via interaction.response.send_message and halts execution by returning None. Upon successful validation, it returns the cleaned username string. When no username is provided, the function queries the RegistrationStore using list_for_user with the invoking user's Discord ID to retrieve their linked tracker accounts. If the database returns an empty list, indicating no prior registration, it sends a specific no-registration embed and returns None. Otherwise, it defaults to the first registered username in chronological order (linked[0]) and returns it. Within the project architecture, this function acts as a critical gatekeeper for the /match command handler. It ensures that downstream API calls to Tracker.gg always receive a sanitized, validated, or properly defaulted username, preventing malformed requests and providing clear user feedback during the resolution phase. The function centrally manages input sanitization, validation routing, and database fallback logic, allowing the /match command to focus exclusively on fetching and displaying match data once a valid username is secured.
**Note**: The function strictly enforces non-blocking execution by awaiting database queries and interaction responses. Callers must check for a None return value before proceeding, as it indicates a resolved failure state requiring immediate termination of the command flow. The fallback mechanism relies on list_for_user returning usernames ordered by registration time, meaning the oldest registered account is automatically selected when no explicit argument is given. Error messages and embeds are hardcoded in French; localization adjustments may be necessary for multilingual deployments. The function assumes the RegistrationStore instance is properly initialized and accessible within the command's scope.
**Output Example**: 
- Explicit valid input: await _resolve_username(interaction, "Player_One-123", store) returns "Player_One-123"
- Explicit invalid input: await _resolve_username(interaction, "Invalid@Name!", store) sends an error embed and returns None
- Fallback with registration: await _resolve_username(interaction, None, store) (user has registered accounts) returns "FirstRegisteredAccount"
- Fallback without registration: await _resolve_username(interaction, None, store) (user has no registered accounts) sends a no-registration embed and returns None
## FunctionDef register_match_command(tree, tracker, store)
**register_match_command**: The function of register_match_command is to define and register a Discord slash command that retrieves and displays recent ranked match details from Tracker.gg for a specified or previously registered user.
**parameters**: The parameters of this Function.
· tree: An instance of app_commands.CommandTree used to bind the newly defined command to the bot's command registry.
· tracker: An instance of TrackerScraper responsible for fetching and caching match data from the Tracker.gg API.
· store: An instance of RegistrationStore used to resolve default Tracker.gg usernames for Discord users who have previously registered their accounts.
**Code Description**: This function acts as a command factory that defines an asynchronous slash command named /match. Upon registration, it attaches metadata describing the optional username parameter. When invoked by a user, the command first logs the request and attempts to resolve a valid Tracker.gg username. If no explicit username is provided, it queries the RegistrationStore to retrieve the user's default registered alias. Once a valid username is obtained, the interaction response is deferred to prevent timeout during data retrieval. The function then delegates data acquisition to TrackerScraper.fetch_match_bundle(), which handles API requests, caching, and rate limiting. Depending on the result, it either sends an embed indicating no matches were found, or constructs a match picker embed alongside an interactive view (MatchPickerView) for user selection. The execution flow includes comprehensive error handling: it catches ProfileNotFoundError for invalid accounts, TrackerRateLimitError for API cooldowns, TrackerScraperError for scraping failures, and a generic exception handler for unexpected issues. Each branch logs performance metrics and sends an ephemeral embed response to the user. The function is invoked during bot startup within MarvelLoggerBot.setup_hook, where it registers the command into the global or guild-specific command tree before synchronization.
**Note**: The function relies on external helper functions (_resolve_username, build_no_matches_embed, build_match_picker_embed) and classes (MatchPickerView) that are not defined within this scope but must be available in the module's namespace. It requires an active asynchronous event loop context for all operations, particularly when awaiting tracker.fetch_match_bundle() and Discord interaction methods. The username parameter is optional; if omitted, the command strictly depends on prior successful registration via /register. Rate limiting and cache eviction are managed internally by TrackerScraper, so this function does not need to implement cooldown logic itself. All responses are sent as ephemeral messages, ensuring only the requesting user sees them.
**Output Example**: 
await register_match_command(tree, tracker, store)
# Returns: None (Command successfully registered to the tree)

Expected Bot Response upon successful execution:
[Ephemeral Embed] Recent Ranked Matches for PlayerOne
- Match 1: Victory | Rank: Diamond | Rating: +25
- Match 2: Defeat | Rank: Diamond | Rating: -18
[Interactive View] Buttons to expand match details...
[Log Output] /match OK pour PlayerOne (3 matchs, 3 détails) — 1.4s
(Note: The function itself returns None; the example illustrates the successful interaction flow and logging output.)
### FunctionDef match(interaction, username)
**match**: The function of match is to orchestrate the execution flow of the /match Discord slash command, resolving user input, fetching match history data from an external tracker service, and rendering interactive UI components or error feedback to the requesting user.
**parameters**: The parameters of this Function.
· interaction: A discord.Interaction object representing the incoming slash command execution context.
· username: An optional string containing the tracker username explicitly provided by the user in the command arguments; defaults to a registered profile if omitted.
**Code Description**: This async function serves as the primary command handler for the /match feature within the Discord bot architecture. Upon invocation, it initializes timing metrics and logs the request context before delegating username resolution to _resolve_username. If resolution fails, execution halts immediately. Otherwise, it defers the interaction response to acknowledge receipt while processing continues in the background. The core logic invokes tracker.fetch_match_bundle to retrieve structured match data for the resolved username. Depending on the outcome, it routes execution through distinct branches: an empty result triggers build_no_matches_embed; a successful fetch constructs a dynamic UI using build_match_picker_embed and MatchPickerView, which is delivered as an ephemeral followup message alongside performance logging. The function implements comprehensive exception handling to manage external service failures. It specifically catches ProfileNotFoundError for missing accounts, TrackerRateLimitError for API cooldowns, TrackerScraperError for scraping infrastructure issues, and a generic Exception fallback for unhandled runtime errors. Each error path logs diagnostic information at appropriate severity levels and returns a standardized user-facing message via build_error_embed. Functionally, this command acts as the central orchestrator that bridges user input, external data acquisition, caching mechanisms, and Discord UI rendering, ensuring robust error propagation and consistent feedback across all execution paths.
**Note**: Points to note about the use of the code
- The function strictly relies on _resolve_username returning a non-None value; callers must ensure downstream logic accounts for early termination during resolution failures.
- Interaction deferral is mandatory before calling fetch_match_bundle to prevent Discord API timeout errors during network operations.
- All followup messages are sent with ephemeral=True, ensuring visibility is restricted solely to the command requester.
- The function assumes tracker.fetch_match_bundle handles its own caching and rate-limiting logic; this handler focuses exclusively on orchestration and presentation.
- Error handling prioritizes user experience by converting technical exceptions into localized embeds while maintaining detailed server-side logging for debugging.
**Output Example**: 
A Discord ephemeral followup message displaying an interactive dropdown titled "Derniers matchs classés — PlayerName123" with a list of recent ranked matches. Upon selecting a match, the message updates to show detailed scoreboard statistics. If the player has no recent matches, an orange embed stating "Aucun match classé récent" is displayed. In case of API rate limiting, a red error embed indicates the required cooldown duration before retrying.
