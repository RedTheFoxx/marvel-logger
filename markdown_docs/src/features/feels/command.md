## FunctionDef _resolve_registered_username(interaction, username, store)
**_resolve_registered_username**: The function of _resolve_registered_username is to validate and resolve a Discord user's requested Tracker.gg username against their registered account list, returning the resolved name or None if validation fails.
**parameters**: The parameters of this Function.
· interaction: A discord.Interaction object representing the current slash command invocation, used to access the invoking user's ID and send ephemeral responses.
· username: An optional string containing the Tracker.gg username provided by the user; defaults to None if not specified in the command arguments.
· store: An instance of RegistrationStore providing asynchronous database access methods for retrieving user registration records.
**Code Description**: This asynchronous helper function acts as a validation and resolution layer within the /feels command workflow. It first queries the RegistrationStore to retrieve all Tracker.gg usernames linked to the invoking Discord user's ID via list_for_user. If the retrieval returns an empty list, it immediately sends an ephemeral embed generated by build_feels_no_registration_embed instructing the user to link an account via /register and terminates by returning None. When a username is not explicitly provided, the function defaults to returning the first registered username in the retrieved list. If a username is provided, it strips surrounding whitespace and performs a case-insensitive comparison against all linked usernames. Upon finding a match, it returns the exact stored candidate string to preserve original casing. If no match exists, it constructs and sends an ephemeral embed generated by build_feels_unknown_username_embed detailing the invalid input alongside the user's registered options, then returns None. Within the project architecture, this function is exclusively invoked by the feels command handler in src/features/feels/command.py. The caller relies on its return value to determine whether to proceed with fetching match data or to abort execution early due to missing or invalid registration data. The function delegates database queries to RegistrationStore.list_for_user and UI generation to build_feels_no_registration_embed and build_feels_unknown_username_embed, maintaining a clear separation between business logic, data persistence, and presentation layers.
**Note**: The function strictly enforces case-insensitive matching while preserving the original casing of stored usernames for downstream API requests. It relies on ephemeral message responses to avoid exposing registration data to other users in the channel. The RegistrationStore must be properly initialized before invocation, and all async calls within this function require proper awaiting. If the linked list contains multiple entries, only the first entry is used as the default fallback when username is None.
**Output Example**: "PlayerOne" or None
## FunctionDef register_feels_command(tree, tracker, store, feels_store)
**register_feels_command**: The function of register_feels_command is to define and bind the `/feels` Discord slash command, orchestrating match data retrieval, existing rating queries, chart generation, and interactive feedback collection for ranked matches.

**parameters**: 
· tree: app_commands.CommandTree - The application command tree instance used to register the new slash command within the Discord bot framework.
· tracker: TrackerScraper - The scraper instance responsible for fetching player profile metadata and recent ranked match bundles from external tracking APIs.
· store: RegistrationStore - The database persistence layer used to resolve default registered usernames when the user does not provide an explicit alias.
· feels_store: FeelsStore - The database persistence layer used to query existing match ratings, retrieve historical season records for visualization, and persist new feedback submissions.

**Code Description**: This function operates as a command factory that registers an asynchronous slash command named `/feels` onto the provided `tree`. When invoked by a user, the internal handler first logs the request metadata and resolves the target player username by evaluating the optional `username` parameter or falling back to the requester's first registered alias via `store`. The interaction response is deferred immediately to prevent Discord API timeouts. The handler then queries `tracker.fetch_match_bundle()` to retrieve the latest ranked matches for the resolved player, enforcing a configurable match limit. If no matches are found, an ephemeral embed notifies the user and exits early. Otherwise, it queries `feels_store` for existing ratings and season-specific historical records. Historical chart data is rendered synchronously via `render_feels_chart` and offloaded to a background thread pool using `asyncio.to_thread` to prevent event loop blocking. The handler calculates unrated matches, constructs an overview embed, and instantiates a `FeelsRatingView` if unsubmitted ratings exist, attaching the followup message reference to enable subsequent interactive state management. Successful execution logs match counts, rating statistics, and execution duration. Comprehensive exception handling is implemented: `ProfileNotFoundError`, `TrackerRateLimitError`, and `TrackerScraperError` trigger specific ephemeral error embeds, while a broad `except Exception` block captures unexpected failures with generic messaging. This function is initialized during bot startup via `MarvelLoggerBot.setup_hook`, where it receives injected dependencies (`tree`, `tracker`, `registrations`, `feels`) to operate within the application's dependency injection context and ensure proper lifecycle management.

**Note**: 
- The function depends on external module-level constants (e.g., `FEELS_MATCH_LIMIT`) and helper functions (`_resolve_registered_username`, `build_feels_no_matches_embed`, `build_feels_overview_embed`, `render_feels_chart`, `build_error_embed`) that must be available in the execution scope.
- Chart generation is executed synchronously inside an async context via `asyncio.to_thread`; calling it directly without offloading will block the Discord event loop and cause interaction timeouts.
- The `FeelsRatingView` instance requires explicit assignment of the followup message (`view.message = message`) to correctly route subsequent user button interactions.
- All database queries and scraper calls are asynchronous; they must be awaited, and synchronous execution will result in deadlocks or unhandled coroutine warnings.
- Ephemeral responses are strictly used for error notifications and match-not-found states to ensure only the requesting user sees sensitive or contextual data.

**Output Example**:

# Usage context within MarvelLoggerBot.setup_hook:

    self.tree, 
    self.tracker, 
    self.registrations, 
    self.feels
)

### FunctionDef feels(interaction, username)
**feels**: The function of feels is to serve as the primary asynchronous handler for the `/feels` Discord slash command, orchestrating username validation, match history retrieval, rating data aggregation, and interactive UI generation.
**parameters**: The parameters of this Function.
· interaction: discord.Interaction - Represents the invocation context of the slash command, providing access to the requesting user and response methods.
· username: str | None - An optional Tracker.gg username provided by the user; defaults to None, triggering automatic resolution of the first registered account.
**Code Description**: This asynchronous function implements the core workflow for the `/feels` command within a Discord bot architecture. Upon invocation, it logs the request and delegates username validation to _resolve_registered_username, which cross-references the input against the user's linked Tracker.gg accounts stored in the registration database. If validation fails or no account is linked, the function terminates early by sending an ephemeral error embed. Once a valid username is resolved, the interaction response is deferred to accommodate subsequent processing time. The function then queries the external tracker service via tracker.fetch_match_bundle to retrieve recent ranked match previews. If no matches are found, it immediately returns a dedicated informational embed. For successful fetches, it normalizes the username and queries the local SQLite database through feels_store.rated_match_ids and list_for_season to determine which matches have already been rated and to gather historical rating records for the current season. If seasonal records exist, the function offloads the synchronous chart generation routine (render_feels_chart) to a background thread pool via asyncio.to_thread to prevent event loop blocking, wrapping the resulting PNG bytes in a Discord file object. An overview embed is constructed using build_feels_overview_embed, which dynamically formats match statuses, seasonal statistics, and average ratings. Unrated matches are filtered from the bundle, and if any remain, an interactive FeelsRatingView component is instantiated to allow the user to select and rate matches via a dropdown interface. The final response is dispatched using interaction.followup.send, attaching the embed, chart file, and view. If a rating view is created, its message reference is explicitly assigned for proper timeout handling. The function concludes with performance logging and implements comprehensive exception handling for ProfileNotFoundError, TrackerRateLimitError, TrackerScraperError, and generic runtime errors, ensuring all failure states are communicated to the user via standardized error embeds without crashing the bot.
**Note**: Points to note about the use of the code
- The function must be invoked within an asynchronous context; calling it synchronously will return a coroutine object rather than executing the workflow.
- Chart rendering is explicitly delegated to a thread pool using asyncio.to_thread; removing this delegation will block the Discord bot's main event loop during image generation.
- The interactive view requires explicit assignment of the returned message object (view.message = message) to enable correct timeout management and state synchronization.
- All error responses are sent as ephemeral messages, ensuring they are only visible to the command invoker and do not clutter public channels.
- The function relies on pre-initialized database connections for feels_store and a properly configured tracker client; missing or misconfigured dependencies will cause immediate failure during execution.

In failure scenarios, the output is replaced by a red-bordered error embed detailing the specific exception (e.g., rate limit cooldown, missing profile, or scraper failure).
